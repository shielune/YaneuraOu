# k-p 評価関数アップグレード候補 — 実装コストと R 上昇の見積もり

最終更新: 2026-04-15

現行の k-p は `suishopetite_20211123.k_p.nnue`(2021 年 11 月の水匠
系で学習された KP256 NNUE)で、2026 年現在の水準から見ると数年分の
学習技術と教師品質の進歩を取りこぼしている。次期 k-p を作る上で
取りうる 4 つの選択肢について、実装コストとレーティング上昇の観点
で優先順位付けを行う。

利用可能なリソース: **A100 × 8(学習 GPU)**、既存の教師データ
**約 300 GB**(評価値付き、ある程度強いエンジンで計算済み)、および
既存の WASM ビルドパイプライン。

---

## 候補一覧

0. **既存の強い評価関数を teacher にした蒸留** — 現行サイズのまま retrain
1. **新しい教師データによる学習** — 現行サイズのまま、300 GB データで retrain
2. **より大きいネットワークモデルへ切り替え** — KP512 / KP1024 / KP2048
3. **NNUE 代替アーキテクチャの開発** — Transformer / Deep MLP 等

---

## 0. 既存の強い評価関数を teacher にした蒸留

### 方針

- Teacher: 水匠 s / illqha4 等の公開されている強い NNUE(**CPU 推論向き**)
- Student: 現行 k-p と同じ KP256 アーキテクチャ
- Loss: `MSE(sigmoid(student_eval / scale), sigmoid(teacher_eval / scale))` (`scale ≒ 600`)
- 学習データ: 既存 300 GB データ(評価値は teacher で再付与 or そのまま使う)

### 実装コスト

| 項目 | 所要 |
|---|---|
| `nnue-pytorch` に KP256 feature transformer を追加 | 3〜5 日 |
| `serialize.py` の KP256 対応(PyTorch ↔ やねうら王 nn.bin の往復) | 2〜3 日 |
| **往復テスト**(既存 `suishopetite.k_p.nnue` を読み込んで再書き出しし、やねうら王で同じ棋力が出ることを確認)| 2 日 |
| 学習パイプライン組み立て | 1 日 |
| 小規模学習(10M 局面 × 数 epoch)で pipeline 健全性確認 | 1 日 |
| **合計** | **1〜2 週間** |

### GPU / CPU コスト

- Teacher 推論: 既存 300 GB データが既に評価値付きなら **0**。再付与する場合 CPU で数時間〜数日
- PyTorch 学習: A100 × 1 で **数時間**、× 2 以上はデータローダー律速で頭打ち
- 棋力計測: CPU で自己対戦 1000〜5000 局

### バイナリサイズ変化

**なし**(1.41 MiB / Brotli 479 KiB をそのまま維持)

### 期待 R 上昇

**+100 〜 +200**

- 現行 k-p は 2021 年の teacher で学習されているため、2023〜2025 年の水匠 s / illqha4 系で再学習するだけで差分で伸びる
- Student capacity が teacher より小さいので teacher 完全模倣は不可、R-150〜-300 のギャップは残る
- それでも現行 k-p より明確に強くなる

### リスク

**低**。既知の技術で、Stockfish / やねうら王系で実績ある枠組み。最大のリスクは serialize.py の量子化 / バイナリレイアウト実装で、ここさえ往復テストで通れば後続の作業は安定する。

---

## 1. 新しい教師データによる学習

### 方針

- Architecture: 現行 k-p のまま(KP256)
- データ: **既存の 300 GB 評価値付きデータ**
- 本質的に候補 0 と同じ流れで、**データソースが既存データセットである点だけが違う**

### 実装コスト

候補 0 との重複を除いた追加コストは以下:

| 項目 | 所要 |
|---|---|
| データパイプライン整備(300 GB のサブサンプリング、shuffle、train/val split) | 2〜3 日 |
| データ品質の検証(評価値の分布、スケール、異常値フィルタ) | 1〜2 日 |
| **合計**(候補 0 と併合した場合) | **候補 0 と同じ 1〜2 週間** |

### GPU / CPU コスト

候補 0 と同じ。A100 × 1 で数時間の学習。

### バイナリサイズ変化

**なし**

### 期待 R 上昇

**+100 〜 +200**(候補 0 と同程度)

### 候補 0 との関係

**候補 0 と候補 1 は実装的には同一作業で、実質的には 1 つのタスク**。差は:

- 候補 0 = 「teacher を決めて評価値を新規生成する」
- 候補 1 = 「既存の評価値付きデータを使う」

**300 GB データが既に手元にある以上、候補 0 の「教師局面を新規生成する」フェーズは省略できる**。つまり Phase 1 として走らせるのは **実態として候補 1**で、候補 0 の方法論(蒸留)をそのまま適用する形が自然。

## 2. より大きいネットワークモデルへ切り替え

### 方針

- Architecture: KP512 / KP1024 / KP2048 のいずれか
- feature 定義は現行 KP のまま、hidden 層のみ拡大(および任意で後段 MLP 深層化)
- 学習は候補 0/1 の pipeline をそのまま流用
- 現代 CPU(AVX-512 VNNI / NEON dotprod)の実効性能向上で hidden 拡大のコストが実質ゼロ

### 実装コスト(候補 0/1 完了後、追加で)

| 項目 | 所要 |
|---|---|
| C++ 側の新 architecture ヘッダ追加(例: `source/eval/nnue/architectures/k-p_512x2-32-32.h`)| 1 日 |
| `nnue-pytorch` 側の hidden 変更 | 数時間 |
| `serialize.py` の hidden 可変対応 | 1 日 |
| 量子化 scale の再調整(層ごとの weight のダイナミックレンジに合わせる) | 1〜2 日 |
| 全体ビルド(wasm edge/node/web 3 variant)と smoke 確認 | 1 日 |
| 棋力計測(自己対戦) | 数日 |
| **合計**(候補 0/1 完了後) | **追加 1 週間** |

### GPU / CPU コスト

- 学習時間は hidden が倍でも A100 側は数倍程度で、半日〜1 日で収まる
- A100 × 8 を使うなら、**複数サイズ(KP512 / KP1024 / KP2048)を並行学習して比較する**のが正攻法
- 棋力計測が bottleneck で、各サイズで自己対戦 1000+ 局

### バイナリサイズ変化

feature 数 ≒ 1,390(現行)で計算した見積もり(詳細は `.claude/skills/wasm-leader/eval_upgrade_plan.md` の別節参照):

| アーキ | wasm 合計 | br 圧縮後 | Workers Free (3 MiB) | Workers Paid (10 MiB) |
|---|---|---|---|---|
| **KP256 (現行)** | **1.41 MiB** | **479 KiB** | ✅ | ✅ |
| KP384 | ~1.75 MiB | ~600 KiB | ✅ | ✅ |
| **KP512** | **~2.10 MiB** | **~720 KiB** | ✅ | ✅ |
| KP768 | ~2.82 MiB | ~960 KiB | ✅ | ✅ |
| **KP1024** | **~3.50 MiB** | **~1.17 MiB** | ✅ | ✅ |
| KP1536 | ~4.90 MiB | ~1.65 MiB | ✅ | ✅ |
| **KP2048** | **~6.30 MiB** | **~2.10 MiB** | ✅ | ✅ |

**現実的な上限は KP1024〜2048**。KP1024 までは Cloudflare Workers の
Free プラン(bundle 上限 3 MiB gzip 後)でも載るので、配信インフラ
制約が実質無視できる。

### 期待 R 上昇

| アーキ | 追加 R 上昇(候補 0/1 完了後の差分) |
|---|---|
| KP512 | +100 〜 +200 |
| KP1024 | +200 〜 +350 |
| KP2048 | +300 〜 +450(逓減) |

**hidden 拡大による棋力寄与は log スケールに近く**、256 → 512 の
伸びが 512 → 1024 より大きい。KP2048 まで行くと追加コストに対する
R 上昇の効率が悪くなる。

### リスク

**中**。具体的な落とし穴:

- **量子化 scale の調整**: 層ごとの weight ダイナミックレンジが変わるので、現行の int8 量子化をそのまま使うと精度が落ちる。試行錯誤が必要
- **WASM SIMD(128-bit)のスループット劣化**: ネイティブ CPU(AVX-512)より 2〜4 倍遅いので、hidden 拡大が nps 減に直結。差分更新が効くのである程度緩和されるが、KP2048 では wasm 実行時の nps が KP256 の半分以下に落ちる可能性
- **学習データ不足**: hidden を増やすとパラメータ数も増えるので、同じデータ量では under-trained になる可能性。300 GB あれば問題ないはず

## 3. NNUE に代わる非線形評価関数アーキテクチャの開発

### 方針

- Transformer / Deep MLP / Graph NN / Hybrid モデル等を新規開発
- Alpha-beta に載るスループット(1 μs 未満/局面)と非線形表現力の両立を目指す

### 実装コスト

| 項目 | 所要 |
|---|---|
| アーキテクチャの設計(性能見積もり、差分更新の可否検討) | 1〜2 ヶ月 |
| プロトタイプ学習(PyTorch + カスタム feature) | 1 ヶ月 |
| C++ 側の evaluate_xxx.cpp 新規実装 | 1〜2 ヶ月 |
| 量子化 / SIMD / 差分更新の最適化 | 数ヶ月 |
| 学習フレームワーク整備 | 数ヶ月 |
| やねうら王本体との統合 | 数週間 |
| **合計** | **6 ヶ月 〜 1 年以上** |

### GPU / CPU コスト

予測困難。学習自体は A100 × 8 でも足りないかもしれない(Transformer 系だと)。

### バイナリサイズ変化

予測不能。非線形層が前段に入ると差分更新が効かず、同じ推論速度を
出すためにはパラメータを削る必要があり、wasm サイズは却って小さく
なる可能性もあるが、後段の計算量が爆発して実用速度を出せない
リスクが高い。

### 期待 R 上昇

**-∞ 〜 +1000**。振れ幅が巨大。

- 成功すれば NNUE を大幅に超える可能性(dlshogi が GPU で示している通り、原理的には表現力の高い NN の方が強い)
- 失敗すれば nps 低下で alpha-beta が回らず、**現行 k-p より弱くなる**(マイナスの R)
- 将棋 / チェス界で NNUE を CPU で超えた成功例は現時点でゼロ

### リスク

**極めて高い**。技術的難易度、開発期間、成功確度のすべてにおいて研究プロジェクト級。

- **差分更新が効かないと alpha-beta が致命的に遅くなる**(1 μs/局面が 10 μs になると実効 nps が 1/10)
- **NNUE は「sparse input × 線形層 × 差分更新」という特殊な組み合わせで高速化されていて、この枠を外すと CPU では勝てない**
- **GPU 前提なら dlshogi が既にある**。NNUE を CPU で置き換える理由がそもそも薄い

### 結論

**研究課題として棚上げ**。実務で手を出すのは非推奨。

## 推奨戦略

候補 0 と 1 は実質同じ作業なので併合し、3 段階で積み上げる形が ROI 最大:

### Phase 1: 蒸留 + 300 GB データ retrain(候補 0 + 1 併合)

- **期間**: 1〜2 週間
- **内容**: nnue-pytorch の KP256 対応 → serialize 往復テスト →
  300 GB データで retrain → 現行 k-p と同サイズの新 weights を生成
- **成果物**: `suishopetite_2026.k_p.nnue` (仮称) — 現行 k-p を
  R+150 程度上回る
- **サイズ**: 1.41 MiB(変化なし)
- **実動確認**: 既存 web/node/edge 全 variant のビルドと smoke が
  そのまま通る
- **最大の gate**: 往復テスト(既存 weights を PyTorch に読み込んで
  再書き出しし、やねうら王で同棋力が出ること)。これが通らないと
  学習を進めても無駄

### Phase 2: KP512 への拡大(候補 2 前半)

- **期間**: Phase 1 完了後 +1 週間
- **内容**: hidden を 256 → 512 に拡大した architecture を追加、
  Phase 1 と同じデータで retrain
- **成果物**: k-p の **KP512 variant** — Phase 1 版から追加 R+150 程度
- **サイズ**: 2.10 MiB(+0.7 MiB)、Workers Free プラン内
- **判断**: Phase 1 で想定通り伸びていれば Phase 2 に進む、
  伸びなかった場合は pipeline を見直す

### Phase 3 (任意): KP1024 への更なる拡大

- **期間**: Phase 2 完了後 +1 週間
- **内容**: hidden を 512 → 1024 に拡大、同データで retrain
- **成果物**: k-p の **KP1024 variant** — Phase 2 版から追加 R+150 程度
- **サイズ**: 3.50 MiB(+1.4 MiB)、Workers Free プランでも余裕
- **判断**: Phase 2 の棋力上昇が有意かつサイズ増が許容できれば進む。
  不要なら Phase 2 で止める

### Phase 4 (棚上げ): NNUE 代替アーキ(候補 3)

- 将来の研究課題として記録のみ
- 現時点では一切リソースを割かない
- A100 × 8 という強力なリソースがあっても、これを 6 ヶ月以上の
  研究に投入するのは ROI が見合わない

| Phase | サイズ | 累積 R 上昇 | WASM 実行速度 | edge 実用性 |
|---|---|---|---|---|
| 現行 k-p | 1.41 MiB | 0 | 速い | ✅ |
| Phase 1 (retrain) | 1.41 MiB | **+150** | 同じ | ✅ |
| Phase 2 (KP512) | 2.10 MiB | **+300** | やや遅い | ✅ |
| Phase 3 (KP1024) | 3.50 MiB | **+450** | さらに遅い | ✅ |

**3 ヶ月以内に現行 k-p を R+450 上回る新 weights を焼ける**のが現実的な最終目標。
Phase 1 のみでも最低 R+150 の改善は見込め、**最初の 2 週間で
はっきりした棋力向上が手に入る**のが最大のメリット。

## 着手の出発点

最初にやるべき調査(Phase 1 に入る前の準備):

1. **nnue-pytorch の現状確認** — `nodchip/nnue-pytorch` fork に
   KP256 feature transformer が入っているか、`serialize.py` が
   やねうら王形式を出力できるかの 2 点
2. **300 GB データの形式確認** — packed_sfen v1 / v2 / HCPE 等の
   フォーマット、評価値の scale、局面の分布
3. **teacher の選定**(候補 1 を採用する場合はスキップ可) —
   水匠 s / illqha4 等の公開 weights の入手先確認
4. **既存 `suishopetite_20211123.k_p.nnue` のバイナリレイアウト
   解析** — 往復テストのための情報収集。具体的には
   `source/eval/nnue/evaluate_nnue.cpp` の `ReadParameters` を
   読み解いて、ヘッダ / feature transformer / affine layer の
   並び順を確定させる

上記 4 つが揃えば、Phase 1 の最初のステップ「**既存 weights を
PyTorch に読み込んで `.bin` に書き戻し、やねうら王で同棋力が
出ることを確認する往復テスト**」に着手できる。

このドキュメントは方針検討用の snapshot であり、Phase ごとの
実績(R 上昇の実測値、学習時間、量子化 scale、ハイパラ)は別途
作業ログとして記録する。
