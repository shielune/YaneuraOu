理由は「V9.00 の Engine class 大規模 refactor で WASM 対応が壊れ、

今回それを書き直し、**upstream 最新 (V9.6x) で WASM が動く状態にした。**

見返り:

  NAGISA_V3 の核心を移植せずに使えるようになる
- NNUE 任意アーキテクチャの動的生成が入ったので、手で配線していた
  HalfKP768 (`17fcf51c`, `3e1f9068`) を削除できる
- 1年半ぶんの探索改良

## 前提: upstream の WASM は壊れていた

「fork のパッチを当て直す」作業ではなく、**upstream の WASM 対応を修理する**
作業だった。以下はすべて upstream 側の実バグで、放置するとビルドは通っても
動かない。

| 箇所 | 症状 |
|---|---|
| `thread.cpp:35-76` | `Thread` の worker 生成が丸ごと `#if !defined(__EMSCRIPTEN__)` の中で、`#else` はコメントのみ。worker が永久に nullptr になり、最初の `go` で `thread.cpp:493` の `th->worker->limits` が null 参照 |
| `thread.cpp` `ThreadPool::set` | `isready` のたびに全 pthread を join して作り直す。ブラウザのメインスレッドから呼ぶとデッドロック |
| `engine.cpp:506-563` `run_heavy_job` | keep-alive スレッドを立てて呼び出し元でスピン待ち。`__EMSCRIPTEN__` ガード無し。NNUE/MATERIAL では `isready` → `Eval::load_eval()` で必ず通る |
| `evaluate_nnue.cpp:697` | `Options["EvalFile"]` を読むのに、登録するコードがどこにも無い。NNUE の `isready` が落ちる |
| `usi.cpp` | `usi_command` が死んだ `#if 0` の中。削除済みのグローバル `Threads` / `usi_cmdexec(pos, states, cmd)` を参照 |

`USIEngine::loop()` に `#if !defined(__EMSCRIPTEN__)` が残っていたこと、
`usi_cmdexec` が「wasm版対応のため関数を分離する必要があった」とコメント付きで
member method として生きていたことは足場になった。

## 実装

### WASM ブリッジ (`1f5a12e6`)

- `usi.cpp` にファイルスコープの `USIEngine*` を置き、`loop()` の EMSCRIPTEN 分岐で登録
- `usi_command` はそこへ委譲。`Thread::threadStarted` が全て立つまでは 1 を返し、
  JS 側に再送させる
- engine と USIEngine は entry point で意図的に leak させる。`loop()` が即 return
  するため、そうしないと最初の ccall が来る前に解体される。
  `EXIT_RUNTIME=0` なので main を抜けてもランタイムは生き続ける

`emscripten_exit_with_live_runtime()` は `postRun` の発火順が読めなかったので
採用しなかった。leak 方式は挙動が確定的で、ランタイム内部に依存しない。

**JS 側の契約は一切変えていない**ので、公開済み20パッケージのローダーはそのまま動く。
`ccall("usi_command", "number", ["string"])` / 0=受理・非0=再送 /
`addMessageListener` で出力受信。

### NNUE の重み配置 (`36dbeb4e`)

em++ ビルドは `-DUSE_SSE42` を渡しており、config.h でこれが
`USE_SSE41` → `USE_SSSE3` と連鎖する。その結果 `GetWeightIndex` が
Stockfish 17 由来の scrambled 配置を選ぶのに、`USE_WASM_SIMD` の `Propagate()` は
dense として読む。正しいバイトを間違った場所から読んでいた。

`affine_transform.h` と `affine_transform_sparse_input.h` で
`USE_WASM_SIMD` のとき dense を強制するようにした (V8.50 と同じ対処)。

### pthread なし経路 (`3f1581cf`)

cfworkers/edge 系8パッケージは `EM_PTHREAD=0` でビルドする。upstream の `Thread` は
コンストラクタの**メンバ初期化リスト**で `std::thread` を作るため、既存の
`#if` ガード (その下にある) では防げず、`-fno-exceptions` なので
`system_error` を捕まえることもできず abort する。

`config.h` に `WASM_NO_PTHREAD` を定義し、`std::thread` メンバごと落として
`run_custom_job` を呼び出し元で同期実行するようにした。
`ThreadPool::set` は1スレッドに畳む (スレッドが無い以上、Worker を増やしても
並列にならず逐次実行で時間が増えるだけ)。

**この構成では `go` が同期呼び出しになる**。`bestmove` を出し終えてから返るので、
`stop` で止められない。呼び出し側は `movetime` か `nodes` で必ず上限を切ること。

### Memory64 (`491cdeaf`)

`EM_MEMORY64=1` でポインタ64bitのビルドができるようにした (`source/Makefile` の em++ ブロック)。

```sh
make tournament COMPILER=em++ TARGET_CPU=WASM \
  YANEURAOU_EDITION=YANEURAOU_ENGINE_NNUE_KP256 \
  EM_MEMORY64=1 EM_PTHREAD=1 \
  TARGET=<out>/yaneuraou.js EM_EXPORT_NAME=YaneuraOu_K_P EM_ENVIRONMENT=node ...
```

既定は 0。4GB のヒープ上限を超えられるので、巨大な評価関数
(halfka_hm2 の 78MB クラス) と大きな置換表を同居させたいときに効く。
速度は 11% 落ち、バイナリは 3% 大きくなる。

Node 26 で動くことは確認済み。**ブラウザや Cloudflare Workers の対応状況は未確認**
なので、公開パッケージに載せる前にターゲットごとの確認が要る。
公開パッケージは 32bit のままにしてある。

## 検証方法

評価の正しさは「同一リビジョンの native ビルドと WASM ビルドが、
同一条件で同じ探索をするか」で見た。

決定的にするために `Threads=1` / `USI_Hash` 固定 / `usinewgame` /
`go nodes` または `go depth` を揃える。この条件が揃うと、評価関数の実装が
同じ変種同士は **bestmove どころか探索ノード数まで一致**する。

結果 (KP256 + 水匠 petite):

| 比較 | 結果 |
|---|---|
| wasm32 pthread vs native scalar (`go nodes 200000`) | 完全一致 (200,131 nodes / cp -75 / `4a3b ponder 2f2e`) |
| wasm32 edge vs native scalar (`go nodes 200000`, hash 16) | 完全一致 (200,042 nodes / hashfull 83 まで一致) |
| wasm node vs wasm browser (`go nodes 1000000`) | 完全一致 (1,000,322 nodes / cp -3) |
| wasm 32bit vs 64bit vs SIMD無し | 完全一致 |

性能の詳細は [`2026-07-28_wasm_v96x_performance.md`](2026-07-28_wasm_v96x_performance.md)。

## 既知の問題

### native と WASM で深い探索が分かれる

局面によっては depth 11 以上で探索ノード数が食い違う (bestmove は一致)。
**V8.50 では起きず、V9.6x で入った**。置換表オーバー・ポインタ幅・SIMD・
コンパイラ・`-ffast-math`・FMA・`std::log`・ソート順はすべて実測で否定済み。
詳細は [`docs/wasm_native_divergence.md`](../docs/wasm_native_divergence.md)。

### native NEON が scalar と食い違う

`TARGET_CPU=GRAVITON2` のビルドは native scalar とも WASM とも違う答えを出す。
gcc と clang の NEON 版が完全一致するので、コンパイラではなく NEON カーネルの
コード自体の問題。**V8.50 にも存在**し、今回の移植とは無関係。

`USE_NEON_DOTPROD` が 9 箇所で参照されているのに**ソースのどこでも定義されていない**
点が怪しい (`-march=...+dotprod` でコンパイルしているのに dotprod 無し扱い)。
配布物は WASM と x86 中心なので実害は限定的だが、ARM ネイティブ
(Apple Silicon 含む) では影響しうる。
